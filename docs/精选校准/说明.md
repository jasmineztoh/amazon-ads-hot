# 精选校准

版本：2026-10-29-v1。状态：等待用户打标。

## 这轮选什么

共48篇真实内容，来自39个信源条目。36篇用于形成标准，另12篇留到标准冻结后验证。来源条目不等于相互独立的机构。覆盖官方公告与教程、基础与进阶方法、客户案例、研究、工具发布、竞争产品比较、观点及节目文字。

不只从已推荐信源挑看起来好的文章；也抽取榜单、通用清单、经营与采购AI、跨平台方法、较早的教程等对照内容。没有用博彩、注册页、404等一眼就能排除的页面凑样本。入选训练样本不表示Agent推荐刊发。

原文正文已逐篇取得并保存本地快照，48篇均有日期和可读文字；44篇本次直连成功，4篇使用2026-10-28保存的正文。节目文字介绍按实际材料标出，不冒充音频转录。图片与视频中的信息仍应点原文查看。全文快照留在忽略目录，不发布到GitHub。

## 怎样打标

打开[待标文章](待标文章.md)，每轮6篇，也可以直接在聊天里进行。

- **要**：愿意让本站向目标读者推荐。
- **不要**：不值得本站推荐，附一句原因。
- **拿不准**：说清缺什么，或哪一点让你犹豫。

无需先填复杂评分或互斥分类。熟悉的基础知识也可以留给新人；这是一项考虑因素，不是预设答案。不要根据厂商、官方或记者身份直接决定。原文观点不等于已被本站独立验证。

回复格式：编号｜要、不要或拿不准｜一句理由。也可直接说第一篇、第二篇，由Agent映射编号。

## 打标之后

1. 用户原话、决定、理由和日期写入[标记.json](标记.json)，以此文件为真实标签记录。文章材料中的human为初始空值，不能将其或Agent原来的判断当成人工标签。
2. 有分歧时先检查摘要是否漏掉证据、限定或宣传承诺，再讨论偏好；不要用摘要失真反推用户标准。
3. 将确认的取舍整理成可复用原则和正反例；暂定推测与已确认规则分开，写入后续精选标准。
4. 用户标“拿不准”时先记录uncertain，材料不足标needs_material；不自动转成框架的either。只有用户明确认为选或不选均可接受时才用either。未标注不能当reject。
5. 标准稳定后，再让用户标留出的12篇，并冻结这一轮规则后评估。验证结果只能报告实际标注和运行的情况；本轮不能据48篇的挑选宣称准确率。

框架原建议100—200条；本项目MVP先用48篇启动，有实际分歧或覆盖缺口再补样本。不是用48篇宣布标准已充分验证，也不是现在微调模型。
